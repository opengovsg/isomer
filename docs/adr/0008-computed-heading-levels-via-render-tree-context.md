# Heading levels (`h1`-`h6`) are computed from render-tree position via a threaded `headingLevel` prop, not hardcoded or author-chosen

Every rendered page must produce a valid heading outline (no skipped levels) so Lighthouse's **"Heading levels skip order (broken page outline)"** audit passes on every page. Today, `renderLayout`/`renderComponent` (`packages/components/src/templates/next/render/`) can't guarantee this: structural components hardcode a fixed tag per component type (`Hero*` always `<h1>`; `InfoCards`, `Infopic`, `KeyStatistics`, `InfoCols`, `Infobar`, `ContactInformation`, `CollectionBlock` always `<h2>`/`<h3>`), and the Prose rich-text editor lets authors pick any heading `level` (2-6) with zero validation against surrounding content. Neither mechanism knows where on the page it actually sits.

The fix computes each heading's real tag from its actual position/nesting in the render tree. No component and no author input can cause a skip, because the tag is derived, never chosen.

**Implementation-mechanism correction (found while implementing, before any code was cut):** the design originally called for a React Context (`HeadingLevelContext` + `<Section>`, mirroring the existing `LinkComponentContext` in `packages/components/src/templates/next/context/`). That turned out to be a dead end: `LinkComponentContext`'s own comment explains React Context only works across a `"use client"` boundary, and per `packages/components/CLAUDE.md`, template components are meant to stay **server-renderable** — confirmed by grepping the tree: `Hero*`, `InfoCards`, `KeyStatistics`, `ArticlePageHeader`, `ContentPageHeader`, and most other heading-emitting components carry no `"use client"` directive, so `useContext` is simply unavailable in them. Since the value being threaded is a plain serializable number (not a function, which is what forced `LinkComponentContext` to use Context in the first place — functions can't cross the server→client boundary as props), the fix instead threads an ordinary `headingLevel: number` prop through the existing render call chain. This preserves every decision below unchanged; only the plumbing mechanism differs.

## Decisions and their reasons

- **Generic, arbitrary-depth prop threading, not a fixed 3-tier enum.** `renderComponent`/`renderPageContent` (`packages/components/src/templates/next/render/`) forward a `headingLevel: number` prop uniformly to every content block, via the existing `...rest` spread. `renderPageContent` special-cases `layout === "homepage"` directly (rather than taking a generic per-caller override prop) to give that one layout's first block `h1` — see the Homepage decision below; every other layout just passes a single uniform `headingLevel`. Components with their own titled sub-items (`InfoCards` cards, `KeyStatistics` stats, `CollectionBlock` items, Collection layout's item cards) pass `headingLevel + 1` down to those items; `Accordion` passes `headingLevel + 1` to its `Prose` children (it doesn't consume a level itself — its own title renders as `<summary>`, not a heading). A shared `getHeadingTag(level)` utility (`packages/components/src/utils/getHeadingTag.ts`) turns the number into `"h1"`-`"h6"`, clamped to a valid range. Chosen over a fixed enum because the schema already has at least two real nesting tiers (top-level blocks, items within a block) with a third reachable via Accordion → Prose, and plain number props absorb any future nesting depth with zero new plumbing.

- **Prose's authored `level` (2-6) becomes a pure visual-style preset, decoupled from the tag.** `Heading.tsx` (`packages/components/src/templates/next/components/native/Heading/Heading.tsx`) used to use `level` to pick both the tag and the `className` (font size). Now it only picks the `className`; the tag comes from the new `headingLevel` prop, via `getHeadingTag()`. All headings rendered within a single Prose block get the same computed tag, regardless of what level the author picked — an author can no longer create a real semantic sub-heading nested under another heading within one block. This was chosen deliberately over preserving relative authored structure: the Studio editor already presents heading levels as a size/style picker (`HEADING_LEVELS` in `apps/studio/src/features/editing-experience/hooks/useTextEditor/constants.ts` caps the choices to 2-5 and remaps `#`/`##` markdown shortcuts to `h2`/`h3`), so treating `level` as structural was already a fiction in practice — and only "fully computed, no author-influenced structure" gives an unconditional zero-skip guarantee for arbitrary content.

- **`getTableOfContents` / `getTransformedPageContent` are unchanged**, still filtering on authored `level === 2` (`packages/components/src/utils/getTransformedPageContent.ts`, mirrored in `Content.tsx`, `IndexPage.tsx`, `Database.tsx`). Now understood as "author picked the 'appears in ToC' style preset," fully decoupled from the real rendered tag. Reworking this to a dedicated non-visual signal was considered and rejected as separate scope beyond the heading-order fix.

- **Per-layout `h1` guarantee, decided per layout rather than one uniform rule:**
  - `Article` / `Content` / `IndexPage` / `Database` layouts pass `headingLevel: 2` into `renderPageContent` — their dedicated header (`ArticlePageHeader`/`ContentPageHeader`) already renders a hardcoded, unchanged `h1` outside the content-block flow.
  - `Collection` layout's page header (`CollectionPageHeader`) is unchanged (hardcoded `h1`), but its item cards (`CollectionCard`/`InternalLinkTitle`/`ExternalLinkTitle`) were found to be a **real, pre-existing violation** while implementing this: they hardcoded `h3` with no intervening `h2` block heading between them and the page's `h1` (Collection has no "block" tier — cards sit directly under the page header). Fixed by threading `headingLevel={2}` from `CollectionClient` down to the cards.
  - `Homepage` (`packages/components/src/templates/next/layouts/Homepage/Homepage.tsx`) has no dedicated header, so `renderPageContent` hardcodes `layout === "homepage" && index === 0 ? 1 : headingLevel` — the assumption that a `Hero` block is present and first; `Hero`'s title becomes the literal `h1`. No defensive fallback is added for legacy Hero-less homepages, even though Studio's own code acknowledges the case (`apps/studio/src/features/editing-experience/utils/getIsHeroFirstBlock.ts`: *"it's not guaranteed that our RootPage will always have a hero banner as the first block"*) — accepted as a pre-existing content/data issue, out of scope for this fix.
  - `NotFound` (`packages/components/src/templates/next/layouts/NotFound/NotFound.tsx`) gains a real `<h1>Page not found</h1>` (was a hardcoded `<h2>`) — a literal, static tag swap since this layout has no dynamic content array at all.
  - `Search` (`EgazetteAlgoliaSearch`) is left **100% untouched** — no `h1`, no `headingLevel` wiring, hardcoded `h3`→`h4`→`h5` stays as-is. Explicitly accepted as the one known exception to the "zero warnings on every page" goal, given it's a 3rd-party embed and low priority.

- **`Hero` appearing inside a non-Homepage layout is not specially handled** — the schema does not restrict the `hero` block type to Homepage, so it can appear in any layout's content array. Rather than adding a schema restriction, this is left to resolve itself: since the tag is computed from the threaded `headingLevel`, `Hero`'s title simply renders at whatever level the surrounding layout provides at that position (e.g. `h2` inside `Article`, since `Article`'s header already consumed `h1`) — never a duplicate `h1`.

- **Internal chrome (`Navbar`, `Footer`, `Siderail`, `Filter`, `SearchableTable`) stays outside the new `headingLevel` wiring**, keeping its current hardcoded `h2`/`h3` tags. This is safe because the heading-order audit only flags a heading that jumps *more than one level deeper* than the deepest level seen so far in document order — it never flags a heading resetting to a shallower/lower number. Nav/footer resetting to `h2` regardless of what main content ended on is therefore never a violation.
  - **`Notification` is the one exception, and needed an actual fix, not just an exemption**: it always renders *above* the page's `h1` (site-wide banner via `Skeleton`), so unlike Navbar/Footer, a heading tag there — even a "safe" low one — would be the very first heading in document order, ahead of the real `h1`. Its title (`NotificationClient.tsx`) was changed from `<h2>` to a plain `<div>` with the identical className, removing it from the heading outline entirely rather than gambling on tag order. (Its embedded `Prose` content can never contain a `heading` block per its own schema — `SimpleProseSchema` only allows `Divider`/`Paragraph` — so passing it a fixed `headingLevel={3}` is inert, just satisfying the now-required prop type.)

- **No regression test is added as part of this work.** The repo currently has no automated a11y enforcement at all (no `eslint-plugin-jsx-a11y`, no axe-core/jest-axe, no Lighthouse CI — only an unwired `@storybook/addon-a11y` panel). Adding one (e.g. axe-core/jest-axe per layout, or a Playwright + axe-core E2E check) is deliberately deferred to a future, separate stacked branch rather than bundled into this change.

## Consequences

- Every layout except `Search` is guaranteed a single, correctly-nested heading outline regardless of what content editors add, remove, or reorder — `Search` remains a known, accepted gap against the "zero warnings on every page" goal.
- Authors lose the ability to express real nested sub-headings (e.g. an `h3` intentionally under an `h2`) within a single Prose block; heading `level` in the editor is now purely a font-size choice. Any future request to bring back real authored sub-structure would require reworking this decision, `getTableOfContents`'s TOC-entry signal, and likely the editor UI's mental model together.
- A Homepage without a `Hero` block as its first content item (legacy GitHub-migrated content, per `getIsHeroFirstBlock.ts`) will still render with no `h1` after this change ships — a pre-existing, explicitly accepted gap, not newly introduced.
- The `hero` block type remains schema-unrestricted per layout; nothing prevents an editor from adding a `Hero` block to e.g. an `Article` page. It will render as a lower-level heading there rather than producing a duplicate `h1`, but no validation stops it from being added in a place it doesn't semantically belong.
- `headingLevel` becomes a required runtime prop on several components' TS prop types (`HeadingProps`, `ProseProps`, `AccordionProps`, `CalloutProps`, `ContentpicProps`, `HeroProps`, `InfoCardsProps`, `KeyStatisticsProps`, `CollectionBlockProps`, and others) — additive to the runtime-only prop set already present alongside `site`/`layout`/`shouldLazyLoad` (not part of the persisted JSON Schema, so no Studio migration is needed), but every Storybook story for these components needed a `headingLevel` value added to its args so story typechecking keeps passing.
- No CI gate exists yet to catch a future regression of this fix (e.g. a new structural component hardcoding a tag again); that remains open until the deferred test-infra work happens.
