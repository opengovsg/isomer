# Image adjustments render from a baked copy but keep the original upload as the source of truth

For the "Adjust image" feature, a saved adjustment is stored as two S3 objects in one asset folder plus the params: the immutable original upload, a baked render copy (the original with crop, rotate and flip applied), and the params `{crop, focal, rotate, flipH, flipV}`. Both objects live under the original's existing `{siteId}/{uuid}/` folder, so they map to one `Asset` and one `AssetLink` in the registry and share that Asset's folder-level visibility.

The page renders the baked copy with `object-position` set from the focal point. The editor always reloads the original plus the params, so every re-edit re-bakes from the original, never from a previous bake. The focal point is never baked. It stays live metadata applied in CSS.

This deliberately rejects the scoping doc's "destructive save" (bake the crop into a new source and discard the previous one). The doc's reasons hold and we keep them: no server-side image processing exists, and the render path is a plain `<img>`. What changes is that we don't throw the original away.

## Context / constraints (verified in this repo)

- **No runtime image-transformation service exists.** `cloudfront.service.ts` is used only for `CreateInvalidation` (cache-busting), and that path is wired only to the admin-only `deleteAssetsByUrl` takedown (`asset.router.ts`). It's a no-op today because the distribution ID is unprovisioned. Cropping at render via URL params would be net-new infra.
- **No server-side image processing exists.** There's no `sharp`, `canvas` or `jimp` anywhere in `apps/studio` or `packages/*`; the only server-side image handling is SVG sanitization (DOMPurify). So the bake has to be a client-side canvas operation.
- **Render is a plain `<img>`.** `ImageClient` (`packages/components/.../internal/ImageClient/ImageClient.tsx`) is a native `<img>`, no `next/image`, no `srcset`. Positioning today is pure CSS (`object-cover`/`object-contain` plus aspect classes).
- **Uploads go browser to S3, never through the app server, by design.** A tRPC presigned PUT returns a URL and the browser PUTs the bytes directly. The reason is resource cost. We don't want image bytes taking up the app server's bandwidth, compute and memory. Keeping un-scanned client bytes off the app tier, behind the GuardDuty scan gate, is a secondary benefit, not the driver.
- **The presign always mints a fresh UUID folder.** `getFileKey` calls `randomUUID()` on every presign and the client can't supply or reuse a key (`asset.service.ts`). So a second object can't land in an existing folder through the presign path without a change.
- **A server-side direct write exists and is key-agnostic.** `putFileDirect` (via `putObjectDirect`) takes a caller-supplied key (`asset.service.ts`, `s3.ts`); its only caller today (`uploadSvg`) passes a fresh `getFileKey`, but nothing forces a new UUID. `copyFile` does an S3-internal `CopyObject` (`s3.ts`).
- **S3 object tagging is strictly per key** (`PutObjectTaggingCommand` per `Key`); nothing is folder-wide. So per-object visibility is mechanically possible, though this design doesn't need it.
- **`.webp`/`.avif` renditions are generated by infra (`isomer-next-infra`), not Studio**, and land in the same folder as the original. The multiple-objects-per-folder shape already exists at runtime; today it's infra-only.
- **The S3 Access Point policy lives in `isomer-next-infra`, not this repo.** It serves only objects tagged `GuardDutyMalwareScanStatus = NO_THREATS_FOUND` with no `deletedAt`. Any new serving condition (say a `private` tag) has to be added there.
- **The renderer reads the page JSON directly**, so a new sibling field is available at render with no extra fetch. `imageFit` is the precedent: a sibling schema field threaded schema → page JSON → renderer → `object-fit` CSS.

## Relationship to the asset-management RFC

This ADR is a consumer of the in-flight ["Refactoring our asset management"](https://app.notion.com/p/opengov/Refactoring-our-asset-management-3b577dbba788806d9328db817b5030f8) RFC, which owns asset mechanics. The RFC adds an `Asset` + `AssetLink` registry, private-by-default assets (an S3 `private` tag), publish-time un-privatization that scans page JSON, and a 90-day sweep of unreferenced assets. Two of its behaviours matter most here:

- **References resolve by folder.** The RFC matches a reference to an `Asset` by the directory portion of `Asset.s3Key`, so any object in a folder counts as using that folder's one `Asset`.
- **Removal acts on the whole folder.** The RFC's removal lists and tags every object in it.

Because the baked copy sits in the original's folder, the baked `src` keeps the folder referenced. That protects the original from the sweep for free and makes original and baked one indivisible lifecycle unit, with a single `AssetLink` to reason about.

**This ADR needs no substantive change to the RFC.** Original and baked share the Asset's folder-level visibility, which the RFC already computes by OR-ing an Asset's `AssetLink` published flags. Once the page is published the whole folder goes public, the original included, and we accept that (see [Visibility](#visibility-folder-level-original-goes-public-with-the-baked)). The one thing to confirm with the RFC authors is a wording clarification; see [the asset-RFC interaction notes](./0010-asset-management-rfc-change-proposal.md).

## Considered options

### Overall approach

- **A. Destructive bake (the scoping doc's choice).** On save, canvas-bake crop/rotate/flip, re-upload, discard the original. It fits the architecture and keeps render trivial, but originals are gone for good, repeated crops compound re-encode loss, and "restore original" is impossible.
- **B. Non-destructive CSS crop, no bake.** Store params only and apply the crop at render with a custom wrapper (`overflow:hidden` plus a scaled, translated `<img>`). Fully non-destructive, but it swaps one `object-fit` class for a custom transform layer that has to survive a responsive cover-frame and rotate swapping the axes. That's a new home for exactly the display bugs this feature exists to kill, and the browser still downloads the full-resolution original for every thumbnail.
- **C. Non-destructive via a new CloudFront/edge transform handler** (`?crop=…&fp=…` URLs). Cleanest render and a bandwidth win, but it's net-new infra in `isomer-next-infra` with its own cost, operations and security to own. Too much for a heroes-only v1.
- **Chosen. "Bake-for-render, preserve-original",** a refinement of A. It keeps A's zero-infra plain-`<img>` render but treats the baked copy as a render cache whose source of truth is `(original + params)`.

### Registry mapping (given the chosen approach)

- **M1. Two folders, two Assets.** The baked copy gets its own presigned upload, so its own folder and `Asset`. To keep the original alive you then need either a scannable path to it in the adjustment object (workable, but two Assets with separately-derived sweep state can drift into a split-brain where one is swept and the other orphaned), or a net-new asset-to-asset "derived-from" relation with its own sweep logic. Either way, two links to keep in sync.
- **Chosen. M2. One folder, one Asset.** The baked object is written into the original's existing folder. Sweep-protection and indivisibility come automatically from the RFC's folder-resolution and folder-removal, and there's a single `AssetLink`.

## Why the chosen option

It removes the two worst risks in the feature's own risk register and adds very little:

- **"Repeated edits degrade quality" → gone.** Re-cropping always starts from the untouched original, so quality never compounds across saves.
- **"Destructive save misunderstood, can't recover originals" → gone.** The original is always there, so "restore original" is trivial and the asset-management work is set up in advance instead of blocked.
- Render stays a plain `<img src={baked}>` with `object-position`. No transform layer (rejects B), no new render-time infra (rejects C).

M2 wins over M1 because it meets the "indivisible unit" and "sweep-protected original" needs structurally, through mechanics the RFC already has, instead of by convention, and it collapses the pair to a single registry link.

## Decisions

### Storage shape and registry (M2)
- The existing `src` string stays the render pointer and points at the baked object, so unadjusted and pre-existing pages don't change and need no migration.
- Adjustment data lives as one optional sibling object on each image-bearing component (absent means "not adjusted"), following the `imageFit` precedent. It stores the params and the original's S3 key. Adding it touches every image-bearing schema and the template renderers, which emit `object-position`.
- Original and baked share one `{siteId}/{uuid}/` folder, so one `Asset` (`s3Key` is the original's key) and one `AssetLink`.

### Visibility: folder-level, original goes public with the baked
- Original and baked share the Asset's folder-level visibility. The RFC computes visibility by OR-ing an Asset's `AssetLink` published flags ("Any `usedInPublished = true` enables public access"), so once any page publishes the image the whole folder, original included, becomes public. While the image is draft-only the folder stays private and the editor loads the original through the RFC's Studio asset proxy.
- No per-object tagging, and no re-tagging on first adjustment. The original just rides the folder's visibility. Nothing special happens at adjust time.
- We accept a publicly-reachable original. The exposure is narrow. The original is never linked on the published site (only the baked copy is in `src`), so you can only fetch it if you already know its exact, unguessable UUID path. The one case where this bites is using crop as redaction to hide sensitive content, and that's a misuse we deliberately don't support. If a genuinely-private original is ever needed, say for a real redaction workflow, per-object visibility within a folder is the way to get there; it's written up in [the asset-RFC interaction notes](./0010-asset-management-rfc-change-proposal.md).

### Byte delivery: straight to S3 (capture both, lean A)
Bytes have to reach the original's folder without passing through the app server. Two workable methods:
- **A (preferred). Presign into the existing folder.** The server builds the baked key inside the original's folder (after an ownership check) and issues a presigned PUT, and the client PUTs straight to S3. This variant must not register a new `Asset`. The cost is teaching the presign to place a key next to an existing asset, plus the ownership check. The upside is that the baked object is just a normal upload: GuardDuty scans it on the same gate every upload uses today, and the Access Point serves it once it carries `GuardDutyMalwareScanStatus = NO_THREATS_FOUND`. There is no new serving behaviour to confirm.
- **G (alternative). Temp upload plus server-side copy.** The client presigns to a fresh temp folder (the standard path, so it gets scanned), then a server call runs an S3-internal `CopyObject` (reusing `copyFile`) into the folder. Bytes never touch the app server. The catch is serving, not just scanning. The Access Point only serves objects tagged `GuardDutyMalwareScanStatus = NO_THREATS_FOUND` (verified in `isomer-next-infra`, `src/s3/index.ts`), and a `CopyObject` creates a new object whose tag state depends on the copy's `TaggingDirective` and on whether GuardDuty re-scans it. If it re-scans, the baked image is unservable (a 403) until the scan re-applies the tag. That behaviour is GuardDuty-managed and can't be confirmed from the repo. Option A avoids the question entirely, which is the main reason it wins.

### Re-save cleanup: unique names, no inline delete
- Each save writes a new baked object with a unique filename (`baked-<uuid>.ext`) and a stem distinct from the original, so their `.webp`/`.avif` variants never collide.
- The superseded baked object isn't deleted inline. A stable-name overwrite, or deleting the old baked on save, would mutate or 404 the still-published page. That's the draft-mutates-published bug the RFC's Immediate Fix removes (it deletes the `deleteAssets`-on-save call).
- So superseded bakeds pile up as bounded folder cruft, cleared only when the whole image is removed and the folder is swept. We accept this. Storage is cheap and the RFC already de-prioritizes exact accounting.

### Reset on replace: release, don't discard
- Replacing the image with a different upload is a fresh presign, so a new folder and `Asset`. Studio clears the adjustment object (the new image starts unadjusted) and repoints `src`.
- The old folder isn't discarded inline. It goes unreferenced and is swept by the normal asset lifecycle (the RFC's linked-but-unused model).

### EXIF and formats
- **Adjustment runs only on static raster (JPEG, PNG, static WebP).** It's disabled (control hidden or greyed) for SVG (vector, and a separate upload path) and for animated formats (GIF, APNG, animated WebP), which a bake would flatten. So the two-objects-in-a-folder shape only ever happens for static raster.
- **EXIF orientation is baked into the pixels** before crop coords are computed (e.g. `createImageBitmap(blob, { imageOrientation: 'from-image' })`). The baked copy comes out upright with EXIF stripped; the original keeps its EXIF, and every re-bake re-normalizes from it.
- **The baked copy is encoded in an infra-optimizable format that keeps alpha** (PNG or WebP when the source has transparency, otherwise JPEG or WebP), so the compression Lambda still produces the served variants. Since the bake always starts from the original, this single re-encode doesn't compound.

## Consequences

- **Saving is now an async step that can fail** (canvas encode plus upload). The original stays until the bake succeeds, so a failed or cancelled save just leaves the previous state in place.
- **Client-side canvas encoding of large sources is memory-sensitive on GSIB tablets.** Something to respect when sizing the bake. This is a client concern; the byte-delivery choice keeps it off the server.
- **Bounded folder cruft** builds up across re-saves and clears on folder removal.
- **No infra change beyond the RFC's own rollout.** Because visibility stays folder-level, this feature needs nothing from `isomer-next-infra` past what the RFC already asks for (the private-by-default `private`-tag scheme and the Lambda's tag propagation). There's no per-object-visibility cross-repo dependency.
- **This isn't full non-destructive editing.** If the product later wants render-time re-cropping (per-breakpoint crops, or serving cropped bytes to save bandwidth), Option C's edge handler is still the upgrade path, and since the source of truth is already `(original + params)`, adopting it wouldn't require re-deriving anything.
